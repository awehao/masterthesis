## 1. 哪一級負責最終輪級限制？

### 提案：最終限制歸**機器人訂閱之 topic 的唯一發布者**

```
gmpc_node ──/cmd_vel_nav──▶ velocity_smoother ──/cmd_vel_smoothed──▶
    wheel_limit_guard ──/cmd_vel──▶ 機器人（Isaac／實機）
```

三項職責重新劃分：

| 層級 | 職責 | 保證什麼 | **不**保證什麼 |
|---|---|---|---|
| `gmpc_node` 出口（現 `fit_to_wheels`） | **內部一致性檢查** | 交給下游的命令在求解器自己的模型內可行 | 不是最終保證；不是硬體加速度保證 |
| `velocity_smoother` | 每軸速率限制（第三方，**不信任其耦合處理**） | 每軸 `max_accel` | 輪級耦合（C 已證違反） |
| **`wheel_limit_guard`（新增）** | **最終輪級限制** | 其輸出的輪速與輪加速度在限制內 | 實際輪子的物理加速度 |

### 為何不改用其他方案

- **改 smoother**：它是第三方套件（`nav2_velocity_smoother` 1.3.12），本機無 `.cpp`；fork 會使版本追蹤更難。
- **只靠 gmpc 出口**：缺口 5 已證不足。
- **靠 `scan_safety_shield`**：它只在 `SHIELD=1` 時啟動（全部 25 趟 bigarena 執行都沒開），職責也不同。

### 裁決：永遠啟用，且為 `/cmd_vel` 唯一發布者

**在這個新基線中成立；不追溯修改舊實驗。**

- **所有**正常控制與**停止**路徑都必須經過 guard——不得有另一個節點平行發布
  `/cmd_vel` 來繞過它（`scan_safety_shield` 若日後啟用，必須接在 guard **上游**）。
- 不可有 `enable=false` 旁路。
- **guard 自身退出時的下游停止**必須明訂：機器人端（Isaac 或實機驅動）需有
  **獨立於 guard 的命令逾時**，在 `/cmd_vel` 停止更新後自行歸零。
  **上游的 guard 不能替自己的失效提供保護**——這一層必須在下游。

## 2. `gmpc` 出口的定位與措辭

`fit_to_wheels` 降級為**求解器的內部一致性檢查**，不再宣稱是最終保證。
其 docstring 目前無條件宣稱「兩個集合都含 `ξ_prev`」，與程式中的零基準退路
矛盾（缺口 2、3），必須改為：

> 相對**上一次 solve 輸出**的檢查；該值不必然是最後發布的命令，
> 且本函式只沿 `ξ_prev → u` 線段搜尋，找不到解**不等於**限制無共同解。

（詳見 §3 對 B2 的更正。）

## 3. 正常運作的限制滿足，與故障／恢復

### 裁決：正常模式**同時**滿足輪速與輪加速度

先前提案把「輪速不可實現、加速度只是追隨不良」分得太絕對——兩者都可能來自硬體
限制，不能把加速度當成可任意犧牲的一方。該提案**撤回**。

**關鍵事實**：在「限制固定、前一筆**已發布**命令已符合輪速、dt ≥ 0」的正常條件下，
兩集合**必定有交集**——保持前一筆命令本身就是一個可行點
（速度集合已滿足；加速度變化為零）。因此正常運作**不需要**放寬任何一項。

| 模式 | 條件 | 行為 |
|---|---|---|
| **正常** | 前一發布命令合法、限制未變、dt 有效 | **同時**滿足兩集合；沿線段取最大可行 λ |
| **故障／恢復** | 前一命令不合法、限制變更、時間異常 | 進入**明確狀態**，恢復取捨另行定義與測試 |

**`accel_relaxed` 不是正常自動退路。** 它只能出現在故障／恢復模式，且必須附
狀態、原因與實際超出量。恢復期間如何取捨（例如允許多少週期、是否限幅）
**需另立規格並單獨測試**，本文不預先決定。

### 「連速度集合都進不去」應視為異常徵兆

對稱的輪速上限集合 `|W·u| ≤ r·ω_max` **包含零**，所以「無法在一步內進入速度集合」
在數學上不該發生。若出現，優先排查：

1. **非有限數值**（NaN／Inf）進入 `u` 或 `ξ_prev`；
2. **無效設定**（`ω_max`／`α_max`／`dt` 為零或負）；
3. **演算法只搜尋了不適當的路徑** —— 這一項是現行實作的真實限制：
   `fit_to_wheels` **只沿 `ξ_prev → u` 的線段**搜尋。當 `ξ_prev` 不可行時，
   該線段可能與可行集不相交，**即使可行集非空**。
   B2 的「無共同解」是在該線段上成立，**不是全域不可行**。

這修正了我先前的表述：B2 證明的是**這條線段搜尋策略在該構造下找不到解**，
不是限制本身互相衝突。

## 4. 前一命令、時鐘與逾時（補齊啟動與中斷）

### 前一筆命令

**guard 自己上一次發布的命令**。保證範圍因此明確限定為
**發布命令序列**，不是實際輪子運動。

### 啟動與重啟：不可直接假設為零

「首筆視為零」**只在啟動流程已確認機器人停止時成立**。
**guard 重啟時，機器人可能仍在執行舊命令**，此時假設為零會低估加速度需求。

提案政策（需實作時明文寫入）：

| 情境 | 政策 |
|---|---|
| 冷啟動且啟動流程已確認靜止 | 前值 = 零，標記 `first_cycle` |
| **guard 重啟、無法確認機器人狀態** | **不得假設為零**；進入故障／恢復模式，先送零並等待一段可設定的安定時間後才回到正常模式 |
| 上游中斷後恢復 | 同上——**不因 dt 很大就接收陳舊命令** |

### 時鐘與時間異常

- 使用**與機器人相同的時鐘**（`use_sim_time` 時為模擬時間），逐筆記錄。
- **模擬暫停**：dt 停止增長 → 不得把暫停期間視為可用的加速度預算。
- **時間倒退或重設**（`/clock` 跳回）：視為時間異常，進入故障／恢復模式，不外插。
- **dt 超過上限**（可設定）：視為中斷，套用上表的「上游中斷後恢復」政策。

### 上游停止發布時

guard **持續執行逾時處置**：超過 `input_timeout` 未收到新輸入即送零，
並在狀態中標記 `input_timeout`。這與 smoother 自身的 `velocity_timeout` 是**兩層**，
不可互相取代。

### 量測什麼間隔

加速度限制必須以 **guard 自己的輸出間隔**計算，**不可用輸入到達間隔代替**。
兩者都要逐筆記錄以便事後核對；C 組目前量到的是輸出訊息的**接收**間隔，
仍不等於發布間隔，這個差距要在驗收中一併記錄。

## 4b. CBF：事後診斷，且必須與原約束對齊

**採用回饋診斷方案**，本輪**不新增 CBF 求解器**。但**下一週期不得拿新的約束評估
上一筆命令，再稱之為該命令的 CBF 殘差**。

### 必須保存並配對的四項

| 項目 | 用途 |
|---|---|
| **命令識別／時間** | 唯一對應一筆最終命令 |
| **對應的約束快照**（`A_cbf_keep`／`l_cbf_keep` 或其識別碼） | 保證評估用的是當時的約束 |
| **原 slack**（`eps` 向量） | 區分「未鬆弛不滿足」與「含鬆弛可行」 |
| **guard 的最終輸出** | 被評估的對象 |

smoother 與 guard 若產生**額外的中間命令**（例如 guard 的逾時歸零），
必須標明它對應哪一組約束、以及該約束的**年齡**。

**無法配對者記為 `not_evaluated`，不得冒充安全通過。**

### 新版本的宣稱（定稿措辭）

> **最終命令符合輪級限制；CBF 對最終命令提供對齊後的診斷，
> 尚不提供端到端障壁保證。**

### 診斷 schema 必須版本化

現行 `/gmpc/diag` 是**位置索引陣列**，22 欄／29 欄的混淆正因為如此。
**只改欄位名不夠**，必須：

1. 加入明確的 **schema 版本欄位**（固定在索引 0 或改用具名訊息型別）；
2. 讀取端遇到未知版本**直接失敗**，不做位置推測；
3. 版本號與程式版本一同記入結果檔。

## 5. 下游 smoother 如何納入驗證？

### 驗收點移到 guard 的輸出

既然 guard 是最終發布者，驗收就在它的輸出量測，smoother 被視為**不可信任的中間層**
（C 已證它會違反耦合限制）。

### 三層測試

| 層 | 內容 | 隔離方式 |
|---|---|---|
| **單元** | `guard` 的純函式：交集、無解、首筆、優先序三種 action | 純 Python |
| **鏈路**（擴充現有 C 組） | `smoother + guard` 串接，灌入命令序列，在 **guard 輸出**量測輪速與輪加速度 | 獨立 domain、測試 topic |
| **回歸** | 重播已記錄的命令序列（含實錄時間間隔） | 同上 |

鏈路測試必須涵蓋：平移＋旋轉、反向、停止、**兩端各自輪級可行但各軸過渡進度不同**
（C 組已有此序列，是它暴露 178.03 的原因）。

### 時間抖動測試的前提

依現況 C 組只能量「輸出訊息序列的接收時間差」。**若 guard 自己記錄每筆的 dt**，
抖動測試就有了可核對的基準，屆時才做。

### 仍然不保證的事（必須寫進結論）

- **實際輪子的物理加速度**：本設計只界定**命令**；模擬器與實機的實際響應未量測。
- **Isaac 的施加方式**：目前以 `set_linear_velocity` 直接施加，不經輪子動力學，
  因此模擬中「命令合規」與「輪子可實現」之間的差距無法由這條鏈驗證。

## 6. 舊行為的可重現性

`wheel_enforce_output=False` **不足以**還原舊結果：這批同時改了 TF 年齡、
障礙逾時（`stale_input_policy='stop'`，**舊版無此停止條件**）、停止狀態機、
以及 relay 的請求序號（**改變控制器跟隨哪條 `/plan`**）。

提案：**不追求逐位元重現**。改為明文宣告
「候選修正版是新基線，舊結果不與之混用」，並保留 `42b963ae` 的原始碼副本
（已存於 `versions/`）。若仍要做等價性測試，範圍**必須限定到確實測過的函式與輸入**。

## 8. 實作與驗收順序

1. 依本文實作，**範圍限定在命令鏈**——不調 heading、Nav2 或感知。
2. 依 A／B／C 做單元與隔離鏈路驗收（驗收點在 **guard 輸出**）。
3. 通過後才安排**一趟** Isaac 短測試，明確標示為「新版本整合驗收」，
   **不接續當成舊 OFF／ON 配對**。
