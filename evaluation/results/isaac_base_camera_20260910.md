# Isaac：底盤相機 RGB 啟用（新設定版本）

日期：2026-09-10。**這是「啟用相機」的新設定，先前無相機影像輸出的凍結結果保留未動。**
相機只用於觀看與記錄，**未接入導航**；深度未開。

## 一、對齊與方向驗證

相機對齊 URDF 的 `base_camera_color_optical_frame`（ROS optical：z 前、x 右、y 下），
以 Isaac 的 `camera_axes='ros'` 交付位姿。**機體座標（相對 `base_footprint`）
(0.2606, 0.0325, 0.3625)** ——不是世界位置；世界位置隨底盤移動。

三軸方向以彩色探針定量驗證（機器人靜止於 seed 1 起點）：

| 探針 | 影像座標 | 針孔模型預測 | 差 |
| --- | --- | --- | ---: |
| 紅（正前 0.80 m） | u=319.5, v=239.5 | 320.0, 240.0 | 0.5 px |
| 綠（再左 0.30 m） | u=191.2 | 193.5 | 2.3 px |
| 藍（正上 0.30 m） | v=110.9 | 113.5 | 2.6 px |

左在畫面左半、上在上半、光軸居中 → **無鏡像、無上下顛倒**。
**同高探針不足以排除上下顛倒**，藍球是為此補的。探針已移除。

## 二、兩個設定版本

| | 規格版（忠於 URDF） | 觀看版（本輪 B 方案） |
| --- | --- | --- |
| 解析度 | 640×480（4:3） | **1600×900（16:9）** |
| 幀率 | 10 Hz | **30 Hz 設定 / 33.3 Hz 實際模擬時間** |
| 水平視角 | 87.0°（hfov 1.518 rad） | 87.0°（同） |
| 垂直視角 | 依 4:3 | **依 16:9，較窄** |
| 內參 fx=fy | 337.4 px | 隨寬度縮放 |
| 原始 topic | 開 | **關**（1600×900 每張 4 MB） |
| 壓縮 topic | 可選 | **開**（JPEG q80） |

**觀看版偏離 URDF 宣告的感測規格**（`base_camera_rgbd`：640×480、10 Hz、clip 0.1–10.0），
不可與凍結結果混用，也不是感測器模型的重現。

## 四、幀率：從 4.3 Hz 到 19–23 Hz

**問題不是「慢」而是「卡」。** 640×480 @10 Hz 的幀間隔是雙峰的：
110–130 ms 佔 88.0%、150–200 ms 佔 11.6%，**沒有任何一幀落在設定的 100 ms**，
約每 5–6 幀頓一次。逐步計時歸因：

| 步別 | 步數 | 中位 | p95 | 最大 |
| --- | ---: | ---: | ---: | ---: |
| 無算圖 | 3600 | 5.84 ms | 6.81 | 14.36 |
| 算圖＋相機 | 400 | **20.19 ms** | **80.48** | **162.96** |

超過 dt 的 403 步中 400 步是算圖步。**相機自身只佔整趟 2.5%**
（讀回 0.35 ms、發布 2.78 ms），卡頓來自 `world.step(render=True)` 本身耗時不穩。

改為 1600×900 後更差（牆鐘 4.3 Hz、RTF 0.418），因為 JPEG 編碼在主迴圈要 **27.34 ms**。

三項改動後的實測（30 Hz 設定、背景編碼、關閉 raw）：

| 解析度 | RTF | 牆鐘幀率 | p90 間隔 |
| --- | ---: | ---: | ---: |
| 1600×900 | 0.510 | 19.3 Hz | **58 ms** |
| 1280×720 | 0.548 | 21.2 Hz | 105 ms |
| 960×540 | 0.586 | 23.0 Hz | 102 ms |

1600×900 幀率略低但**間隔最穩定**。正式一趟：JPEG 平均 **35.4 KiB**、
bag 錄到 6580 張、**零丟棄**、CPU 峰值 83 °C 未觸線。

背景編碼器的佇列深度 2，滿時**丟最舊的幀**——即時觀看優先顯示新幀。

## 五、本輪修掉的四個缺陷

1. **場景沒有光源**：`DomeLight` 原本只在 GUI 分支建立，headless 算圖得到三張全黑影像。改為一律建立。
2. **相機內參用了 USD 預設**：水平視角 23.7°，而模型宣告 87.0°。改為由 URDF 的 `horizontal_fov` 反推焦距。
3. **到達判準硬編碼 0.25**：v2（0.30）只寫進了紀錄文件，**沒有進到程式碼**，所以真值 0.273 m 仍被判 `task_timeout`。改為 `--arrive-tol` 參數、啟動時印出並存入結果檔。以淨空短距案例驗證：`goal_reached_truth`，t=3.11 s、0.286 m ≤ 0.300 m。
4. **`camera_info` 與原始影像耦合**：寫在 `publish_image` 內部，關閉 raw 就一併關掉，整趟未發布任何內參。已抽為獨立方法，每幀都發。

## 七、附帶發現：機器人側向移動，車頭不朝行進方向

實測（1600×900 那趟）：`|vy| > |vx|` 佔 **80.0%**，vy/vx 中位 1.43，
`|wz|` 中位 **0.0015 rad/s**，全程 yaw 只變 **−4.3°**，
**行進方向與車頭夾角中位 124.3°**（0° 為前進、90° 為純側移）。

成因是控制器參數，**不是模擬器**：`gmpc_params.yaml` 的 `Q_y: 0.0`（註解自述「isotropic」，
橫向與前向權重相同）、`R_vx = R_vy = 2.0`（側移與前進代價相同）、
`vy_max` 與 `vx_max` 同級，且代價函數**沒有朝向項**。全向底盤在這組權重下平移比轉身便宜。

第四次報告是純底盤、無相機，車頭方向不影響任何指標，所以此行為此前未被視為問題。
**加裝相機後車頭方向才變得有意義。未改動控制器任何參數。**
