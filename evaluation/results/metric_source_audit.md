## 三、安全計算本身用的是什麼

`wholebody_safety_filter` 的三個限制**全部作用在命令上**，這是設計而非疏漏——它們限制的是
「要求硬體做什麼」：

| 限制 | 作用對象 | 定義 |
| --- | --- | --- |
| 速度盒 | **命令** `v` | `\|v\| ≤ vmax` |
| 加速度盒 | **命令** `v` 與**上一次命令** `v_prev` | `\|v − v_prev\| ≤ amax·dt` |
| jerk 盒 | **命令**的二階差分 | `\|a − a_prev\| ≤ jmax·dt`，`a = (v−v_prev)/dt` |
| 屏障列 | **命令** `v` × **實測幾何** | `n^T J(q) v ≤ α(d − ρ − d_stop)`，`q` 來自實測狀態 |

**屏障是唯一混合的一項**：矩陣由**實測姿態**建立，不等式作用在**命令速度**上。這是正確的
——它問的是「以目前實際姿態，這個命令會不會讓某點以太快的速度接近障礙」。但也因此，
**它保證的是命令滿足約束，不保證實際運動滿足**；實際運動是否跟隨命令，是模擬器／硬體的問題，
必須另外量（見第五節）。

## 四、發現的兩處問題

### 4.1 進度報告的「jerk p95」其實是**命令加速度**的 p95

`analyze_new_TEST.py` 的計算是

```
accel = diff(cmd_vec)/dt          # 速度的一階差分 = 加速度
out['jerk_vx'] = p95(|accel|)
```

**一階差分是加速度，不是 jerk**（jerk 是二階差分）。程式自己的說明寫的是
「std of finite-difference **accel**」，但輸出欄位命名為 `jerk_*`，進度報告也以「jerk p95」
引用。

同時它取自 **`/cmd_vel`（命令）**，不是實際運動。

**受影響的結論**：第一階段四方法比較中所有以「jerk」為名的平滑度數字。**數值本身沒有錯**
（它確實是那個量的 p95），**錯的是名稱與被賦予的意義**。

**建議**：欄位與報告一律改稱**「命令加速度 p95（m/s²、rad/s²）」**。若真的需要 jerk，必須
另算二階差分，並明確標示是命令 jerk 還是運動 jerk。**不需要重跑實驗**——原始 bag 仍在，重算
即可。

### 4.2 `smooth_*` 與 `jerk_*` 都來自命令，與「實際運動平滑度」不是同一件事

兩者都取自 `/cmd_vel`。在**無接觸**且模擬器完整追蹤命令時，兩者接近；一旦有接觸，
實際運動與命令會明顯分離（本輪實測：底盤擦過障礙時實測速度掉到命令的 31%）。

**受影響的結論**：任何把這些數字說成「機器人運動有多平滑」的敘述。正確說法是**「命令有多平滑」**。
要談實際運動平滑度，需改用 `/odom` 或 `/model/<name>/pose` 重算。

## 五、命令與實際運動的分離：本輪實測

| 工況 | 命令 | 實測 | 追蹤率 |
| --- | ---: | ---: | ---: |
| 開闊直線（y = 3.0，無接觸） | 0.100 m/s | **0.1000 m/s** | **100.0%** |
| 速度變更（同工況） | 0.05 / 0.15 / 0.00 | 0.0500 / 0.1500 / 0.0000 | 逐一跟隨 |
| 擦過 `obs_1`（有接觸） | 0.100 m/s | 0.031–0.054 m/s | **31–54%** |

**無接觸時命令與實測一致；有接觸時顯著分離。** 這是「安全層保證命令滿足約束」與「實際運動滿足
約束」之間差距的直接量測。

## 六、底盤停止：兩種模式（本輪重測，橋接已驗證送達）

| | zero（發布零命令） | silence（停止發布） |
| --- | --- | --- |
| 穩態追蹤 | 100.0% | 100.0% |
| 零命令 → 首次判定低於門檻 | **34 ms** | **4 s 觀測窗內未低於門檻** |
| 該區間 odom 淨位移 | 0.00 mm（最後非零命令起算 2.40 mm） | 持續以 0.1 m/s 前進 |

**明確送出零命令能使底盤停止。** 停止發布後，**在 4 秒觀測窗內未觀察到命令逾時或減速**——
更長時間的行為未測，因此不寫成「沒有逾時機制」。

**這不能直接驗證 `arm_vel_gate`。** 命令路徑依組態而異：第二階段全身堆疊中 `arm_vel_gate` 是
`/cmd_vel` 的唯一發布端，由它負責送零；第一階段導航中 `/cmd_vel` 由 `gmpc_node` 發布，該節點
在無計畫、到達容差內或 TF 查詢失敗時自行發布零 twist。

**但那是節點正常執行時的保護分支，不是 watchdog。** 它只在節點還在跑迴圈時生效；節點卡住或
退出後，`/cmd_vel` 上就沒有任何東西再送零，而 `VelocityControl` 會保持最後一個命令。第一階段
的底盤命令路徑因此**沒有涵蓋「發布端本身失效」的機制**。此情境列入 Isaac 的停止驗收。

### 重複位姿樣本：先前的判讀已更正

先前寫「28% 重複樣本會製造假的零速度」。**核對後不成立**：

| | 零命令前 | 零命令後 | **確定仍在運動的區間** |
| --- | ---: | ---: | ---: |
| zero 模式 | **0.0%** | 99.1% | **1.7%** |
| silence 模式 | 4.1% | 0.0%（仍在動） | **2.2%** |

重複幾乎全部發生在**車已停住之後**，時間戳仍照常前進（34.0 ms）。這是停車的正常表現，**不是
資料陳舊**，反而支持 zero 模式確實停住。運動中的重複僅 1.7–2.2%。

**實際停止時間與距離仍受取樣限制**：`/odom` 30 Hz（設定值 `odom_publish_frequency = 30`），
可用的較高頻真值 `/world/.../pose/info` 約 58 Hz，都不足以解析毫秒級的停止過程。取樣間未觀測
到的運動無法排除。**毫秒級停止時間保留為未解析的限制。**

## 七、作廢的測試

橋接未啟動期間（gz 端 `/cmd_vel` 顯示 **No publishers**）的所有量測**一律作廢**，不納入任何
比較：包含「追蹤率約 30%」、「零命令無反應」、「停止發布無反應」。當時底盤執行的是更早以
`gz topic` 原生發布的殘留命令，ROS 命令從未送達。
