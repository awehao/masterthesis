# 模型高度修正 ＋ 狀態資料過期驗證

日期：2026-09-08。本檔的結果全部屬於**新模型版本**。舊模型版本的結果保留在
`wholebody_pregrasp_20260908.md` 與 `pregrasp_demo_20260908.md`，**不可與本檔混算**。

## 一、我先前三個關於幾何的說法是錯的

### 1. collision 與 visual 的比較混了座標系

先前記「圓柱 z 0.10–0.28 對 mesh z 0.00–0.28」。圓柱用的是 base_footprint 座標、mesh 用的是
base_link 座標，而且上緣也記錯。統一到 **base_link**：

| | z 範圍 | 半徑 |
| --- | --- | ---: |
| visual mesh `chassis_frame.stl` | [0.0000, 0.2800] | 0.300 |
| collision 圓柱（origin 0.14、length 0.18） | [0.0500, 0.2300] | 0.300 |
| 支撐球（修正後 origin 0、radius 0.05） | [−0.0500, +0.0500] | 0.05 |
| 輪轂 rim（origin 0、視覺半徑 0.0285） | [−0.0285, +0.0285] | 0.0285 |

正確說法是：**collision 圓柱比 visual 上下各短 0.05 m**，半徑一致（皆 0.300）。此項**未修**。

### 2. 接地面是滾子，不是輪轂

我把 `rim` 的視覺半徑 0.0285 當成輪子外緣來推導。全向輪的接地面是**從動滾子**：

- 滾子中心距輪軸 |xy| = 0.0396（每輪 18 顆，z = ±0.01）
- `roller_omni_wheel.stl` 半寬 0.0090–0.0100
- ⇒ 有效外半徑 **0.0486–0.0496**，與 URDF 宣告的 `wheel_r = 0.05` 相符

先前那句「輪子懸空 0.05 m」結論對，但**推導用錯半徑**，數字是碰巧吻合的。

### 3. 支撐球高度：修正與其限制

`omni_bot.urdf.xacro` 的支撐球關節原點原為 `${-wheel_r}`，球半徑也是 `${wheel_r}`，所以球最低點
在 base_link 下方 **0.10**，而輪子接地線在下方 **0.05**——**支撐球比輪子低整整一個輪半徑**，
gz 把模型撐在球上，輪子必然懸空，與生成高度無關。改為 `xyz="${x} ${y} 0"`。

**這只修正離地高度，不改變接觸模型。** 輪圈與滾輪仍是純視覺，接地仍是四顆零摩擦球，底盤仍由
`VelocityControl` 直接驅動。因此可驗證運動學與命令限制，**不能**據此宣稱輪地打滑、牽引力或
真實煞車能力。

### 四項一起改，否則只改 Gazebo 而控制器仍用舊高度

| 位置 | 舊 | 新 |
| --- | ---: | ---: |
| `omni_bot.urdf.xacro` 支撐球原點 z | −0.05 | **0** |
| 五個 launch 的生成高度 `-z` | 0.05 | **0.0** |
| `wholebody_pregrasp.py` / `pregrasp_demo.py` 的 `MODEL_Z` | 0.05 | **0.0** |
| `barrier_stack.py --spawn-z` / `base_tf_bridge.py --z` | 0.05 | **0.0** |

這四個舊值互相吻合，所以補償是隱形的：只改其中一個都不會報錯，只會讓控制器在舊座標系工作。

## 二、`pregrasp_reference` 必須重算

新模型下**原封不動重跑**，結果是停滯偵測報出：

> 命令已連續 41 週期低於 0.0020，但位置誤差仍 **47.4 mm**、姿態誤差 **0.46°**。解算收斂到
> 非目標的駐點，不是時間不夠。

原因：`pregrasp_reference` 是**舊車高**的 IK 輸出，車身降 0.05 m 後那個臂形已放不到目標，姿態項
與任務項互相抵銷。這正是該值註解寫的「屬於那個目標與這個幾何，要重算不是手改」。

重算（同一目標、同一 0.24 m 標稱距離、底盤 −0.15）：

| | 舊 | 新 |
| --- | --- | --- |
| `pregrasp_reference` | [0, 0.6518, 0.5886, 0, −1.634, 0] | **[0, 0.3641, 0.5263, 0, −1.4086, 0]** |
| IK 殘差 | — | 位置 0.000 mm、姿態 0.000° |

## 四、狀態資料過期：watchdog 不能替代，實測

### 先修正我先前的錯誤說法

我曾說「把 `max-data-age` 從 0.30 放寬到 0.50 s 不影響安全，因為真正的安全停止是閘門的 150 ms
watchdog」。**這是錯的。** 閘門檢查的是「多久沒收到**命令**」，看不到那些命令是用多舊的狀態算
出來的。狀態凍結但上游持續用舊值算出並發布新命令時，watchdog 全程認為正常。

### 鏈路上實際有哪些檢查

| 資料 | 檢查者 | 門檻 | 行為 |
| --- | --- | ---: | --- |
| 命令 | `arm_vel_gate` | 150 ms | 同時歸零底盤與手臂 |
| 命令 | `wholebody_safety` `max_cmd_age` | 250 ms | 輸出零 |
| JointState | `wholebody_safety` `max_joint_age` | 300 ms | 輸出零（reason 3） |
| 距離點雲 | `wholebody_safety` `max_points_age` | 300 ms | 列變 NODATA → **限速降級**，不是停止 |
| 底盤 TF | `wholebody_safety` `max_tf_age` | 300 ms | **本次新增**（reason 6） |

`max_tf_age` 之前**不存在**。`_base_q()` 以 `lookup_transform(..., Time())` 取「最新可得」，
發布端停掉後它會無限期回傳最後一筆，不丟例外也不警告。

### 故障注入實測（命令全程以 20 Hz 持續發布，從未中斷）

| 故障 | feed 實際停止 | 命令歸零 | 自 feed 停止起 | 安全節點 reason | 其他 feed |
| --- | ---: | ---: | ---: | --- | --- |
| 無（基準） | — | 未歸零 | — | ok | 全部 ≤ 36 ms |
| JointState 停 | +1293 ms | +1685 ms | **392 ms** | 關節過期 | odom 68 ms、TF 33 ms |
| 底盤 TF 停 | +107 ms | +426 ms | **319 ms** | 無/過期 TF | JointState 75 ms、odom 79 ms |
| /odom 停 | +38 ms | +473 ms | **435 ms** | 無/過期 TF | JointState 128 ms |

三種故障**底盤與手臂都同時歸零**。JointState 的 1293 ms 是 `ros2 control` CLI 生效所需時間，
不是鏈路延遲。

### 反事實：修正前會怎樣

把 `max_tf_age` 設為 1000 s 以重現修正前行為，同一個 TF 故障：

> TF 於 74 ms 後停止，**TF 年齡達 7937 ms，鏈路從未歸零**，reason 全程 `ok`，機器人持續執行
> 用將近 8 秒前的底盤位姿算出的命令（手臂 −0.0246 rad/s、底盤 −0.0093 m/s）。

閘門全程未察覺，因為命令一直有到。這就是「watchdog 不能替代狀態新鮮度檢查」的實測證據。

### 測試本身的兩個缺陷（已修）

1. 故障注入原本用同步 `subprocess.run`，`ros2 control` 阻塞約 1.5 s，那段期間測試程序既不 spin
   也**不發命令**，於是量到 1698 ms 與一個假的「命令過期」——是測試自己把命令扣住了。改為背景
   執行。
2. 原本用 SIGKILL 殺橋接程序，觸發堆疊 launcher 的 fail-fast，整個堆疊跟著收掉，歸零時間混進
   收拾流程。改為 **SIGSTOP 凍結、SIGCONT 恢復**：程序仍存在，只是不再發布，這才是要注入的故障。
