# 模型高度修正 ＋ 狀態資料過期驗證

日期：2026-09-08。本檔的結果全部屬於**新模型版本**。舊模型版本的結果保留在
`wholebody_pregrasp_20260908.md` 與 `pregrasp_demo_20260908.md`，**不可與本檔混算**。

## 一、我先前三個關於幾何的說法是錯的

### 1. collision 與 visual 的比較混了座標系

先前記「圓柱 z 0.10–0.28 對 mesh z 0.00–0.28」。圓柱用的是 base_footprint 座標、mesh 用的是
base_link 座標，而且上緣也記錯。統一到 **base_link**：

| | z 範圍 | 半徑 |
| --- | --- | ---: |
| visual mesh `chassis_frame.stl` | [0.0000, 0.2800] | 0.300 |
| collision 圓柱（origin 0.14、length 0.18） | [0.0500, 0.2300] | 0.300 |
| 支撐球（修正後 origin 0、radius 0.05） | [−0.0500, +0.0500] | 0.05 |
| 輪轂 rim（origin 0、視覺半徑 0.0285） | [−0.0285, +0.0285] | 0.0285 |

正確說法是：**collision 圓柱比 visual 上下各短 0.05 m**，半徑一致（皆 0.300）。此項**未修**。

### 2. 接地面是滾子，不是輪轂

我把 `rim` 的視覺半徑 0.0285 當成輪子外緣來推導。全向輪的接地面是**從動滾子**：

- 滾子中心距輪軸 |xy| = 0.0396（每輪 18 顆，z = ±0.01）
- `roller_omni_wheel.stl` 半寬 0.0090–0.0100
- ⇒ 有效外半徑 **0.0486–0.0496**，與 URDF 宣告的 `wheel_r = 0.05` 相符

先前那句「輪子懸空 0.05 m」結論對，但**推導用錯半徑**，數字是碰巧吻合的。

### 3. 支撐球高度：修正與其限制

`omni_bot.urdf.xacro` 的支撐球關節原點原為 `${-wheel_r}`，球半徑也是 `${wheel_r}`，所以球最低點
在 base_link 下方 **0.10**，而輪子接地線在下方 **0.05**——**支撐球比輪子低整整一個輪半徑**，
gz 把模型撐在球上，輪子必然懸空，與生成高度無關。改為 `xyz="${x} ${y} 0"`。

**這只修正離地高度，不改變接觸模型。** 輪圈與滾輪仍是純視覺，接地仍是四顆零摩擦球，底盤仍由
`VelocityControl` 直接驅動。因此可驗證運動學與命令限制，**不能**據此宣稱輪地打滑、牽引力或
真實煞車能力。

### 四項一起改，否則只改 Gazebo 而控制器仍用舊高度

| 位置 | 舊 | 新 |
| --- | ---: | ---: |
| `omni_bot.urdf.xacro` 支撐球原點 z | −0.05 | **0** |
| 五個 launch 的生成高度 `-z` | 0.05 | **0.0** |
| `wholebody_pregrasp.py` / `pregrasp_demo.py` 的 `MODEL_Z` | 0.05 | **0.0** |
| `barrier_stack.py --spawn-z` / `base_tf_bridge.py --z` | 0.05 | **0.0** |

這四個舊值互相吻合，所以補償是隱形的：只改其中一個都不會報錯，只會讓控制器在舊座標系工作。

## 二、`pregrasp_reference` 必須重算

新模型下**原封不動重跑**，結果是停滯偵測報出：

## 四、狀態資料過期：watchdog 不能替代，實測

### 先修正我先前的錯誤說法

我曾說「把 `max-data-age` 從 0.30 放寬到 0.50 s 不影響安全，因為真正的安全停止是閘門的 150 ms
watchdog」。**這是錯的。** 閘門檢查的是「多久沒收到**命令**」，看不到那些命令是用多舊的狀態算
出來的。狀態凍結但上游持續用舊值算出並發布新命令時，watchdog 全程認為正常。

### 鏈路上實際有哪些檢查

| 資料 | 檢查者 | 門檻 | 行為 |
| --- | --- | ---: | --- |
| 命令 | `arm_vel_gate` | 150 ms | 同時歸零底盤與手臂 |
| 命令 | `wholebody_safety` `max_cmd_age` | 250 ms | 輸出零 |
| JointState | `wholebody_safety` `max_joint_age` | 300 ms | 輸出零（reason 3） |
| 距離點雲 | `wholebody_safety` `max_points_age` | 300 ms | 列變 NODATA → **限速降級**，不是停止 |
| 底盤 TF | `wholebody_safety` `max_tf_age` | 300 ms | **本次新增**（reason 6） |

`max_tf_age` 之前**不存在**。`_base_q()` 以 `lookup_transform(..., Time())` 取「最新可得」，
發布端停掉後它會無限期回傳最後一筆，不丟例外也不警告。

### 故障注入實測（命令全程以 20 Hz 持續發布，從未中斷）

這些是**命令歸零時間**，不是實際停止時間。量到的是「故障被偵測後，底盤與手臂命令共同歸零」，
命令歸零之後機器還要多久真的停下、期間又走了多遠，本輪**沒有量**。

| 故障 | feed 實際停止 | 命令歸零 | 自 feed 停止起 | 安全節點 reason | 其他 feed |
| --- | ---: | ---: | ---: | --- | --- |
| 無（基準） | — | 未歸零 | — | ok | 全部 ≤ 36 ms |
| JointState 停 | +1293 ms | +1685 ms | **392 ms** | 關節過期 | odom 68 ms、TF 33 ms |
| 底盤 TF 停 | +107 ms | +426 ms | **319 ms** | 無/過期 TF | JointState 75 ms、odom 79 ms |
| /odom 停 | +38 ms | +473 ms | **435 ms** | 無/過期 TF | JointState 128 ms |

三種故障**底盤與手臂命令都同時歸零**。JointState 的 1293 ms 是 `ros2 control` CLI 生效所需
時間，不是鏈路延遲。

#### 這些時間都超過停距公式用的 τ = 0.15 s

$d_{stop} = d_0 + v\tau + v^2/(2a) + \varepsilon$ 裡的 $\tau = 0.15$ s 是**正常控制路徑**的
反應時間。故障反應時間是 319–435 ms，**兩到三倍於它**。

**因此不能再說 τ = 0.15 s 已涵蓋資料失效情境。** 兩者必須分開記錄：

| | 值 | 涵蓋什麼 |
| --- | ---: | --- |
| 正常控制延遲 τ | 0.15 s | 命令正常流動時的反應 |
| 故障反應（命令歸零） | 0.32–0.44 s | 狀態 feed 停止到命令歸零 |
| 命令歸零 → 實際停止 | **未量** | — |
| 故障期間位移 | **未量** | — |

若要宣稱故障期間也安全，還需要獨立量測後兩項，並用故障反應時間而非 τ 重新計算停距。本輪不作
此宣稱。

### 反事實：修正前會怎樣

把 `max_tf_age` 設為 1000 s 以重現修正前行為，同一個 TF 故障：

> TF 於 74 ms 後停止，**TF 年齡達 7937 ms，鏈路從未歸零**，reason 全程 `ok`，機器人持續執行
> 用將近 8 秒前的底盤位姿算出的命令（手臂 −0.0246 rad/s、底盤 −0.0093 m/s）。

閘門全程未察覺，因為命令一直有到。這就是「watchdog 不能替代狀態新鮮度檢查」的實測證據。

### 測試本身的兩個缺陷（已修）

1. 故障注入原本用同步 `subprocess.run`，`ros2 control` 阻塞約 1.5 s，那段期間測試程序既不 spin
   也**不發命令**，於是量到 1698 ms 與一個假的「命令過期」——是測試自己把命令扣住了。改為背景
   執行。
2. 原本用 SIGKILL 殺橋接程序，觸發堆疊 launcher 的 fail-fast，整個堆疊跟著收掉，歸零時間混進
   收拾流程。改為 **SIGSTOP 凍結、SIGCONT 恢復**：程序仍存在，只是不再發布，這才是要注入的故障。

## 尚未處理

- collision 圓柱比 visual 上下各短 0.05 m，未修。
- 距離點雲過期只降級不停止，未單獨做故障注入。
- `max-data-age`（執行端 0.50 s）與安全節點的 0.30 s 是兩個不同的檢查，前者只決定測試何時放棄。
- 本輪屏障全程未介入，對屏障無任何宣稱。

# 追加：底盤碰撞幾何對齊 ＋ 距離資料過期注入

## 五、底盤根本不在屏障裡

修 collision 圓柱時發現的、比圓柱本身嚴重得多的問題：

**`base_link` 從來就不在 `ARM_LINKS` 裡。** 屏障約束十個手臂連桿，**車體本身沒有任何幾何約束**。
底盤固定時看不出來；底盤一旦進入解算，車體可以開進障礙物而每一條屏障殘差都回報滿足——因為
沒有任何一條列描述車體。

要讓「Gazebo、距離計算、安全檢查用同一版幾何」，需要三件事一起做：

### 1. collision 圓柱涵蓋整個車體

視覺 mesh 在 base_link 座標 z ∈ [0.000, 0.280]，且**兩端都到滿半徑 0.300**：底部盤
z 0.000–0.080、頂板 z 0.260–0.280，中間只有 z 0.180–0.200 是細柱（r 0.110）。原本
length 0.18、centre 0.14 的圓柱只涵蓋 z 0.050–0.230，**2688 個 mesh 頂點有 1386 個（51.6%）
落在碰撞體之外**，含兩端的滿半徑區。改為 **length 0.28**（z 0.000–0.280）。細柱段被填成滿
半徑是**保守方向**；兩端沒涵蓋不是。

### 2. 屏障讀不懂 primitive

`link_collision_tris` 只處理 `<mesh>`，primitive 直接跳過。底盤的 collision 是圓柱，所以把
`base_link` 加進 `ARM_LINKS` 會**靜默無效**。新增 `_primitive_tris`，圓柱／方塊／球體皆可
三角化，且多邊形以 `1/cos(π/seg)` 放大成**外接**而非內接——內接多邊形比真實形體小，由它算出的
每個距離都會偏大，正是安全模型不能偏的方向。seg = 32 時代價為半徑的 0.5%。

### 3. 兩份 link 清單各自實作，必然會分家

`arm_link_names` 自己也判斷「有沒有 mesh collision」，所以底盤進了取樣器卻沒進名單，啟動時
撞上 `link order disagreement` 斷言。**若兩份清單長度剛好相同，這個斷言不會響，每一列都會接到
錯的連桿。** 已改為 `arm_link_names` 直接由 `link_collision_tris` 導出，一個函式決定，兩端讀它。

### 認證取樣（含底盤）

| link | 點數 | 認證 ρ |
| --- | ---: | ---: |
| **base_link** | **1200** | **28.12 mm** |
| link_base | 362 | 14.32 mm |
| link1 / link2 / link3 | 226 / 362 / 226 | 13.65 / 12.78 / 12.78 mm |
| link4 / link5 / link6 | 362 / 141 / 55 | 13.54 / 12.62 / 13.30 mm |
| gripper / finger1 / finger2 | 88 / 8 / 8 | 13.35 / 12.73 / 12.28 mm |

底盤 ρ = 28.12 mm 是撞到 1200 點取樣上限的結果（車體表面積約 1.09 m²，遠大於任一手臂連桿）。
ρ 偏大是保守方向，代價是底盤被多推開 28 mm。

### 列數上限與耗時

把上限暫時放到 400（確定不咬）量測，各連桿最大 band：**base_link 90**、link2 77、link4 62、
link1 48、link_base 38、link5 33、link6 31、gripper 25、link3 19、指 5。總列數最大 392。

上限由 60 改為 **100**（高於觀測最大值 90）。這是**單一情境的觀測最大值，不是所有姿態的證明**，
所以丟列數每週期照常發布：一旦非零，該週期的涵蓋保證即失效，而且會說出來。

另外 `barrier_stack.py` 自己有一份 `--max-rows-per-link` 預設 60，會覆蓋節點的值——所以節點
改成 100 之後**完全沒生效，列仍在被丟**。已改為預設 None、不傳就不覆蓋。**在 launcher 裡重複
一次預設值，就是多一個地方會錯。**

耗時代價（安全節點 solve）：

| | 純手臂 179 列 | 含底盤 392 列 |
| --- | ---: | ---: |
| p50 | 10.85 ms | **12.13 ms** |
| p95 | 11.75 ms | **26.75 ms** |
| max | 13.18 ms | **32.62 ms** |

實際週期 dt p50 50.0 / p95 50.0 / max 51.0 ms，**無 deadline miss**，但 50 ms 預算的餘裕明顯
變薄，列為已知風險。

### 新幾何下的回歸（同一案，全零起點）

位置 816 → **0.54 mm**；姿態 89.5° → **0.000°**；底盤停放 **−0.1505**；同動累計 **3.29 s**
（最長連續 2.28 s）；底盤速度最大 0.2597（限 0.2775）超限 **0**；手臂最大 1.1254 rad/s；
屏障輸入違反 **0**；模型下界最小 **230.5 mm**；丟列 **0**。

含底盤後，模型下界代表的是**整車最近點**而非只有手臂；本案最近者仍是手臂（底盤停在 −0.15，
車體前緣約 x = 0.15，離箱面 0.39 m）。

## 六、距離資料過期：限速降級，不是停止

條件：JointState 與 TF 正常更新、上游命令持續發布、**只凍結 `arm_link_distance`**。

第一次測命令下 0.05，看不出任何變化——因為 `nodata_speed_cap` 剛好**就是 0.05**，命令等於上限。
改以 0.20 m/s 與 0.4 rad/s 重測：

| | 故障前 | 凍結中（6 s） | 恢復後 |
| --- | ---: | ---: | --- |
| 手臂命令中位 | 0.4000 | **0.0306** | 12 ms 內回復非零 |
| 底盤命令中位 | 0.0135 | **0.0465** | — |
| NODATA 列數中位 | 0 | **274** | 0 |
| 安全節點 reason | ok | **ok（全程未變）** | ok |
| 命令歸零 | — | **從未歸零** | — |

機制符合設計：feed 過期 → 每列轉 `STATUS_NODATA` → `cap = nodata_speed_cap = 0.05`，且該 cap
**一體套用到所有自由度**（底盤 m/s 與手臂 rad/s 共用同一個數）。

**這不能算安全。** 障礙物距離完全未知時，0.05 m/s 仍足以撞上：本次 6 秒中斷，底盤以中位
0.0465 m/s 前進，約可走 **0.28 m**。而且 `reason` 全程為 `ok`，**唯一可見的訊號是 `n_nodata`**——
不看那一欄就完全看不出距離資料已經死了。

尚未處理：降級期間是否應改為停止、或至少讓 `reason` 反映降級，屬設計決策，本輪未改。

## 七、本輪仍不能宣稱的事

- 「命令歸零」不是「實際停止」；命令歸零後的停止時間與位移**未量**。
- 故障反應 0.32–0.44 s 是 τ = 0.15 s 的兩到三倍，停距公式**未**以故障反應時間重算。
- 距離資料過期只降級不停止，且 `reason` 不反映。
- 列數上限 100 高於**單一情境**的觀測最大值，非全姿態證明。
- 底盤 ρ = 28.12 mm 受取樣上限所限，未達 15 mm 目標。
- 本輪屏障全程未介入（最近 230 mm），對屏障作用無任何宣稱。
