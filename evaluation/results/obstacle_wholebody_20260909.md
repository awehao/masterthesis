# 有障礙的同動預抓取

日期：2026-09-09。世界 `arm_barrier_test.sdf`（目標箱 `obs_0` 未移動，新增底盤障礙 `obs_1`），
資料 `evaluation/results/wholebody_pregrasp.json`。

## 結果分類

依既定驗收表，本次落在**第三格**：

> **安全停住，但無法到達** → 保護有效，繞行／任務完成能力不足。

但比「停住」更細緻：**底盤確實繞了 226 mm 讓開**，只是最後停在離目標 225.9 mm 處。

## 一、先處理的兩個缺口

### 距離資料整批過期 → 停止（不再是限速降級）

安全節點新增 `reason 7`：距離 feed 整批過期時輸出零。原本轉為 `nodata_speed_cap = 0.05` 的
限速降級**不是更保守**——實測 6 秒中斷期間底盤命令中位由 0.0135 升到 0.0465 m/s，機器人在不知道
任何障礙距離之後反而**走得更快**，因為那個 cap 比任務當下要求的還鬆。障礙距離完全未知時，沒有
任何速度站得住腳。

（更正：先前寫的「0.0465 × 6 ≈ 0.28 m」只是風險量級示意，**命令中位數乘時間不是實測位移**。
測試已改為分別量「命令歸零」與「實際停止」及其間位移，本輪尚未在新策略下重跑該項。）

### 帶被截斷 → 報錯並停止（不再靜默丟列）

`max_rows_per_link` 預設改為 **0＝不截斷**，完整帶照發。若有人設了上限且咬到，距離節點在雲中送出
一列 `STATUS_OVERFLOW`，安全節點以 `reason 8` **輸出零**。理由：涵蓋論證是對**整條帶**成立的，
留下最近的 N 條再繼續宣稱涵蓋，並不成立。旗標走雲而不走 diag，因為那是消費端會讀的通道。

實測：完整帶 361 列，丟列 **0**。

## 二、障礙位置是算出來的，不是擺出來的

**先試「擋住直線中段」，那不存在。** 底盤起點 x = −0.70、無障礙解停在 x = −0.15，路徑 0.55 m；
底盤有效半徑 0.328 m（0.300 ＋ 認證 ρ 28 mm）。兩端的淨空圓沿整條路徑重疊，要有只擋中段的位置，
路徑至少得 2 × 0.328 = 0.656 m。要求起點模型間距 ≥ 30 mm 時最深侵入只剩 **8.1 mm**（是雜訊不是
約束）；≥ 35 mm 則**完全無解**。第一次擺出來的位置起點間距僅 4.8 mm，執行時直接被 20 mm 中止
門檻擋下。

**改為擋住「底盤原本想停的位置」**，這反而問了更利的問題：底盤不能停在它要的地方時，全身解算
會不會另找位置停、讓手臂補足差額？

`obs_1`：中心 (−0.225, −0.320)，尺寸 0.16 × 0.20 × 0.60。

| 位置 | 模型間距 |
| --- | ---: |
| 底盤起點 (−0.70, 0) | **+124.0 mm**（跑得起來） |
| 名義停放點 (−0.15, 0) | **−108.1 mm**（被擋住） |
| 偏移 (−0.15, +0.15) | +41.9 mm（可行） |
| 偏移 (−0.15, +0.20) | +91.9 mm（可行） |

十二個 +y 偏移的底盤位姿離線檢查**全部**通過 IK 與整段路徑檢查，所以「停住但到不了」是協調能力
問題，不是任務不可能。障礙寫在世界檔，距離節點由**同一份檔案**產生障礙規格，執行期間不搬動。

## 三、實測結果

| 量 | 結果 |
| --- | --- |
| 底盤軌跡 | (−0.700, 0.000) → (−0.150, **+0.226**)，yaw 0.0° |
| **屏障介入** | 輸入違反 **1105 / 1154** 週期，最大 resid_in **+58.80 mm/s** |
| **輸出違反** | **0**，最大同時作用 **83** 列 |
| 模型下界最小 | **110.5 mm**（無接觸） |
| 姿態誤差 | 90.0° → **0.00°** |
| **位置誤差** | 816.9 → **225.9 mm**（未到達） |
| 命令削減（作用期間） | 入 \|max\| 0.1000 → 出 **0.0000** |

**保護行為有效**：屏障在九成六的週期上限制輸入，輸出從未違反，全程最近 110.5 mm，沒有接觸；
底盤被推離原本的直線 226 mm，繞過了障礙。

**任務未完成**：TCP 停在 (0.30, **+0.2259**, 0.55)，目標 (0.30, 0, 0.55)。誤差
**完全在 y**（−225.9 mm，x 與 z 皆為 0），數值等於底盤的側移量——底盤被逼開多少，TCP 就偏多少。

## 四、為什麼停住：任務控制器只指向被擋住的方向

停滯時的命令：

```
cmd_in   底盤 [0.0, -0.1, 0.0]     手臂 [0, 0, 0, 0, 0, 0]
cmd_out  底盤 [0.0, -0.0, 0.0]     手臂 [0, 0, 0, 0, 0, 0]
```

**手臂命令在進入屏障之前就已經是零。** 不是屏障把手臂停掉的，是解算器從頭到尾沒有要求手臂做
任何事。屏障做的只有一件事：把底盤那個 −y 的要求擋掉。

而手臂其實做得到。從停滯時的底盤位姿 (−0.150, +0.226) 解 IK：

- **IK 成功，整段路徑檢查通過**
- 需要臂形 [−0.8615, 0.7031, 1.1004, −0.9013, −1.3161, 0.3083]
- 與現況差最大 **0.901 rad**，底盤完全不必再動

機制是三件事疊起來：

1. 任務誤差全在 −y；
2. 加權最小平方把它全派給底盤（`base_weight = 3`，底盤較便宜），而底盤正好被擋；
3. 姿態項殘差 **0.00001 rad**——已經滿足，正把手臂釘在原本的形狀，沒有任何項要求手臂接手。

**權重是偏好，不是備援。** 單步加權最小平方在底盤被擋時，沒有任何機制把任務重新指派給手臂；
解決冗餘的姿態項定義在關節空間，並不知道底盤被擋住了。

這正是後續 W-GMPC 要補的：能看到未來數步的解算器會發現底盤的約束，進而選一個由手臂補償的構形；
單步解算做不到，因為每一瞬間最便宜的方向就是被擋住的那個方向。

**沒有調低 margin 讓它通過。**

## 五、順帶修掉的一個潛在缺陷

`pregrasp_demo.target_pose` 原本以「z 中心最低的箱子」選目標。世界裡只有一個箱子時無歧義，加入
第二個之後**靜默選錯**：底盤障礙比目標箱矮，於是每次離線檢查都改瞄障礙物，對一個實際只差
226 mm 的執行報出 1006 mm 誤差。已改為**按名稱**選（預設 `obs_0`）。執行本身不受影響——所有
run 都以 `--target` 明確指定座標。
