### 1. 契約核對的三項必修

**① HOLD 窗口取錯。**

[分析程式](/home/howardchen/masterthesis/evaluation/door_k3ab_lw_contract_check.py:98) 固定使用 18–19.5 s，但任務紀錄顯示：

- lw_1：HOLD 約 18.72–19.76 s。
- ev_1：HOLD 約 19.40–20.42 s。

原窗口包含 ENGAGE，不能整段稱為 HOLD。ev_1 的 OPEN 起點也不是目前傳入的 20.50 s。請由逐趟相位事件取得窗口，保存來源，輸出 r2、不覆寫 r1。

我按上述時間初步重算，真正 HOLD 的命令仍約為 `(＋3.36, −2.01) mm/s`，位姿差分仍很小，**主要觀察沒有因此消失，但數字必須更新**。

**② 相關性不能證明錯位一個物理步。**

請刪除：

> 本列角速度對應下一個 world.step；同列角與速指向不同物理步區間。

瞬時速度與前向區間平均位移，本來就是不同量；較高相關不能單獨證明 API 延遲或時間錯配。改為：

> 在所選窗口，紀錄角速度與前向一步角度差分的相關較高；尚不能據此確認 API 的時間語意或延遲。

「長窗平均不受一步時移影響，所以不是時序造成」也過強。請對**相同區間**比較左端、右端或梯形速度積分與角度增量，量化時移後殘差，再描述結果。

**③ 平均值較大不代表保護較早觸發。**

刪除說明中的「方向上會較早觸發」。窗口平均比值不能證明逐步峰值、觸發時間或漏報情況。

保留：「兩種量的幅值不一致，現有結果不足以判定保護保守或失效。」

### 2. 下一步：先完成 API 語意查核

我讀到本機安裝版 `RigidPrim`：**physics handle 有效時**，姿態走 `_physics_view.get_transforms()`，角速度走 `get_velocities()`；無效時另有回退路徑。因此目前不能直接歸因於「USD 姿態與 PhysX 速度不同步」。

請限定查核：

- 實際載入版本、方法分支與 handle 有效條件。
- 根部速度 setter/getter 的作用對象、座標與時序。
- `world.step()`、狀態更新及相關物理設定的呼叫鏈；未保存的運行時設定列為未知。

完成後，把仍缺的證據收斂成**一份最小取證規格**：同一步分別記錄寫入前、寫入後、物理步後的根位姿／速度，以及門扇姿態／速度、實際 API 參數與步號。既有關節反力可沿用，不必先擴充大量新感測。先送規格，不直接開跑。

### 3. 門速保護暫不替換

**目前不核可直接改成角度差分。** 差分窗口會帶來延遲、平滑與缺步處置問題，不能視為等價替換。

可以先離線比較原始角速度與因果差分候選，核對峰值、觸發時刻、缺步及初始化行為；線上不能使用前向差分所需的未來樣本。之後再決定並行監看或替換版本。

lw_1 的停止結論維持不變；**5 mm 門檻不變，K3-M 停止進入條件仍未解除。**
