## 1. 持續保持：新增終端前狀態 HELD（取代「DONE 後停發」）
**監督器**（求解端，ActiveHoldSupervisor 的版本化擴充；**不改既有門檻**）
- 新序列：`LOWSPEED → ZERO_PUB → CONFIRM → STOPPED →（觀察滿 10 s）→ HELD`。
- HELD 期間：
  - **照常發布主動保持命令**：手臂零命令、底盤錨點伺服；
  - **照常監看停止判準**（同 STOPPED）；任何一項越界 ⇒ FAIL（moved_in_held）⇒ 既有中止。
- HELD 只會被兩件事終止，任何計時都不會讓它自行結束或停發：
  - **(a)** 下一段的交接確認（§2）；
  - **(b)** 中止、失效（§3）。
- 舊的 DONE 語意改稱「**觀察通過**」，作為一個事件記錄，不再代表結束。

**任務端**：pause 觀察通過後，進入 `HELD_WAIT_HANDOVER` 相位，**不送 /room/stop**；持續監看心跳、幾何、走廊。
- 有時間上限：例如 HELD 最長 T_held＝60 s。逾時走正常結束，此時才送 /room/stop，並標「未交接」。

**執行端**：無變化。仍逐步記 applied_src 與走廊、包絡監看；暫停期手指上限 20 N 維持（§4）。

## 2. 交接：請求、ack、來源序號與首筆實際套用證據
交接沿用既有封裝與握手樣式（cmd_env 的 run_id／source_seq、K3-M 模式／暫停握手）。原則：**同一時刻只有一個來源被套用；切換在明確物理步；新來源未證實接手前，舊來源不停發。**

| 步 | 誰 | 內容 |
|---|---|---|
| H1 | 任務端 | 送 `/door/handover_req {run_id, seq, from: 'held', to: <下一段>, req_step}` |
| H2 | 下一段控制來源 | 開始發布自己的封裝命令（新 segment 標籤、獨立 source_seq 區間）。此時執行端**仍只套用 held 來源**，新來源只進候選緩衝，不套用 |
| H3 | 執行端權威 | 新來源連續 ≥ N 筆新鮮且合法（比照 p2c：N＝20；年齡 ≤ 鏈逾時）時，在物理步 k 切換套用來源，回 `/door/handover_ack_exec {seq, switch_step: k, first_source_seq}` |
| H4 | 執行端 | 第 k 步 applied_src 記新來源 source_seq＝**首筆實際套用證據** |
| H5 | 舊來源（held 監督器） | 收到 ack 且看到 applied_src 首筆新來源後，才停止發布，並記 `held_released {switch_step, first_applied_seq}` |
| H6 | 判定器 | 核對：switch_step 前每步套用 held 來源、之後每步套用新來源；中間沒有「無來源」步（鏈模式全為 0）；沒有任何一步同時存在兩來源；舊來源停發晚於首筆新來源套用 |

**拒絕條件**（執行端回 nack，held 繼續保持）：
- run_id／seq 不符；
- 新來源不足 N 筆，或命令過期；
- 已中止；
- 請求在 HELD 之前。
- 被拒絕時不重試切換，由任務端依 §3 處理。

## 3. 優先順序（高 → 低）
1. **中止**：任何監看越界、讀回異常、夾持監看中止。走既有 K2 閂鎖：鏈內命令過期、底盤減速、手臂凍結、夾爪凍結於當下目標、上限維持當下值。中止後不交接、不恢復上限。
2. **失效**：
   - 心跳逾時、求解端停發、觀察器失效 ⇒ 執行端鏈逾時停止路徑＋任務端中止。
   - 交接期間任一來源失效：新來源失效 ⇒ 不切換、held 繼續（若 held 也失效 ⇒ 中止）；切換後新來源失效 ⇒ 中止，不回切 held，以免雙重控制。
3. **逾時**：HELD 超過 T_held、交接請求後 T_ack 內未切換 ⇒ 正常結束（送 /room/stop），標「未交接」；不放爪、不恢復上限。
4. **正常**：交接完成 ⇒ 下一段開始。

以上是既有處置的延續，**不是已驗證的故障後安全停止**。

## 5. 有界、非阻塞的紀錄方案
**問題**：同步重寫整份 JSON 會讓控制迴圈的耗時隨紀錄長度增長。

**方案**（任務端、求解端、執行端同一做法）
- **逐筆 append 的 JSONL**：控制迴圈只把一列放進**有界佇列**，例如容量 4096，用 put_nowait，不阻塞。
  - 寫入由背景執行緒負責：append 後定期 flush。
  - 佇列滿 ⇒ 丟棄並記 `n_dropped` 與第一筆丟棄的時間；判定器視為紀錄不完整。
- **每列多記兩個欄位**：`wall_mono`（單調牆鐘）與 `src_sim_t`（來源模擬時間）。另記每輪迴圈耗時的統計：最大值、p99，以及超過門檻的次數。
- **完整 JSON 摘要只在結束時寫一次**，且在迴圈外。中途只寫輕量心跳檔，例如每 1 s 覆寫一行狀態。
- **判定器 trace 核對**：
  - 以 JSONL 為準；
  - 同時檢查來源步連續、wall_mono 間隔、n_dropped＝0、寫入端落後量（佇列最大深度）；
  - 不以重寫完整度推定連續。

**離線／假世界反例**（實作時一起交）
1. **寫入端停滯**：背景寫入執行緒每筆 sleep 1 s。
   - 核對控制迴圈週期維持名目值、trace 的來源步沒有大於門檻的間隙；
   - 佇列深度增加並被記錄；
   - 結束時佇列排空，或標記未寫完。
2. **佇列溢出**：容量設 10、寫入停滯 ⇒ n_dropped > 0 ⇒ 判定器判紀錄不完整（不通過）。
3. **同步重寫對照**：重現舊做法（每 100 筆同步重寫），在假世界量迴圈最大耗時隨筆數增加，作為候選原因的離線佐證。這只是佐證，不等於實錄根因。
4. **主迴圈卡住**：注入 0.5 s 的 sleep ⇒ 判定器以 wall_mono 與來源步偵測出間隙 ⇒ 不通過。
