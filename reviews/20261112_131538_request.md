# TO_PRE 途中追蹤誤差：既有紀錄診斷＋同鏈假世界對照（一個修正）

提交 `git log -1`。診斷只讀 m8house_da_approach_1 紀錄；對照全是**假世界**。r4 控制器檔未動（雜湊相符）。

## 1 時間與起點（`資料/door_approach_track_diag_approach_1.json`）
- 重算時參考起點（當下實測關節）對實測 TCP 差 0.004 mm；當下手臂速率 0.0015 rad/s、參考起始速度 0。參考延後 8 步（命令生效時刻）才開始。沒有接續差。
- 同時刻誤差最大 51.65 mm（由紀錄重建；控制器紀錄 51.69）。時間位移掃 0–0.4 s：最好 δ＝0.15 s 仍有 40.3 mm。實測 TCP 到參考曲線最近距離最大 40.3 mm。⇒ **是路徑偏離，不是時間落後**。（我原先猜是延遲＋一階落後造成的時間差，紀錄否定了。）

## 2 參考可行 vs 命令可行
- 關節參考峰值 0.9999 rad/s（＝上限 1.0，bounded_T 用 V_ARM＝1.0 定時長）；含一階設定點模型所需設定點速率峰值 1.009。名目上貼著上限、沒有餘裕，但這不是主因：
- 參考是關節內插再 FK 成 TCP 路徑。沿參考 Jacobian 最小奇異值由 0.095 降到 **0.0088（t≈10.3 s，q5 經過 0.28 附近）**。求解器只追 TCP、線性化點是「命令為零」（u_arm_nom 未給）。以實測構型算追 TCP 參考所需關節速度：9.9 s 前 <0.9，10.1 s 2.4、**10.3 s 9.9 rad/s**。
- 實測：9.7 s 起 q1／q4／q5 偏離關節參考（最大 0.61 rad）而 TCP 誤差仍小（10.2 s 3.4 mm），之後 q1、q5 頂 −1.0 rad/s 追趕，TCP 誤差升到 52 mm。設定點速率飽和 1.55 s（9.73–11.37 s）。
- 判讀：近奇異處以零命令為線性化點的單步線性化追不上，關節路線走岔，再以飽和追回。未做的區分：若把時長拉長是否也能過（沒試，因為那是用時間換誤差）。

## 3 選定的一個修正：關節名目線性化
`door_approach_jnom_ctrl.py`（r4 的版本化複本；`joint_nominal=False` 預設與 r4 逐值相同——兩個失配案追蹤、終端、淨空全等）。開啟時，底盤固定相位把重算的關節軌跡經設定點模型反算成名目命令，交給 gmpc_wb 既有的 `arm['u_arm_nom']`：
s_ref＝q_ref＋τ·q̇_ref−bias/α；u_k＝clip((s_ref(t_{k+1})−s_k)/dt, ±v_arm)。沒有新增增益；代價、速度／加速度上限、參考時長、淨空門檻、停止掃掠都不變。gmpc_wb.py 未改。
