## 2. 為什麼沒有到 ZERO_PUB（只描述）
監督器 LOWSPEED 要求四項窗口速度同時低於門檻並連續 hold_s；8 s 內沒有達成，42.85 s 記 `timeout`。四項的門檻是：
- 底盤平移 1 mm/s；
- 底盤轉動 0.005 rad/s；
- 門 0.002 rad/s；
- 實測手臂各關節 1e-3 rad/s。

以房間逐步紀錄、0.1 s 位姿差分重算（同判準）：
- 底盤平移 35.8 s 起 ≤ 0.6 mm/s，37.8 s 起 ≤ 0.3 mm/s；底盤轉動 ≤ 0.0021；門 ≤ 0.0015 rad/s。**底盤與門大致已停**。
- **手臂是擋住的一項**：
  - 各關節 p95 速度 0.003–0.017 rad/s（j4 最大），8 s 內移動範圍 1–14 mrad（j3 14.5 mrad）。
  - 只在 38.8 s 附近有一段 94% 的樣本全部低速，之後又動。
- hold 階段底盤命令不是 0：停車伺服朝錨點推，約 (2.4, −1.4) mm/s。但底盤只偏離錨點約 (−0.8, −1.1) mm，實際幾乎沒動。
- 觀察：底盤經夾持與門相連；伺服持續推、底盤不動，同期求解端以手臂持續修正凍結目標的追蹤。
  - 這與 W-GMPC 既有的「手臂高頻振盪未解」可能有關，未驗證，不推定根因。

## 3. 其他判定理由
- `grasp_finger_contact_below_min`：PAUSE 中 41.87 s 時 finger2 降到 0.47 N。
  - 策略允許短暫失接觸（finger_loss_s），所以未中止；判定器逐步要求 ≥ 0.5 N，所以記失敗。
- `k3m_executor_violation`：45.61 s 走廊偏航越界，發生在中止（42.90 s）之後的觀察期。
- `door_angle_pre_open_over_1deg`、`finger_bar_outside_allowed_phase`、`trace_unverifiable`：pause_1 起各趟都有的既有理由。
- **`pause_frozen_target_not_last_published` 是判定器數值偽拒**：
  - 凍結目標與 PAUSE 前最後一筆已發布目標（seq 364）逐元素差 1.1e-16。
  - 原判定器用 acos 算旋轉差，同一矩陣自比就得 3.65e-8 rad，超過 1e-9 門檻。
  - 以 `door_k3m_check_p2r2.py`（穩定算法 2·asin(‖ΔR‖_F／2√2)，門檻不變）重判：旋轉差 1.1e-16，該理由消失。
  - 原判定器輸出 `door_k3m_check_p2.json` 保留，r2 輸出另存 `door_k3m_check_p2r2.json`。
