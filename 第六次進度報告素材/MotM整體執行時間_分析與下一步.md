# MotM 整體執行時間：已確認分析與下一步

更新：2026-10-05。依使用者指示，近期工作優先解決「MotM 完整流程應比停車流程更短」的問題；這是改善目標，不是已有結論。本次只讀既有資料，沒有跑新模擬或修改控制程式。

## 已確認：目前 MotM 不比停車快

b6 公平對照：停車／MotM 各 3 趟、交錯執行，同一抽屜、抓取幾何與任務判準。兩組皆使用多步控制，因此這是**任務策略比較**，不是 H1／H5 的時域比較。

| 指標 | 停車 | MotM |
|---|---:|---:|
| 完成 | 3/3 | 3/3 |
| 開始移動→完成，平均 ± 標準差 | 77.7 ± 1.2 s | 80.2 ± 1.7 s |
| 不允許停頓 | 每趟 5 段 | 每趟 0 段 |

本批 MotM 平均多花 **2.47 s**。證據支持減少停頓與移動中夾持，不支持「端到端更快」。三趟不提供統計穩定性；也不能把這次結果寫成「MotM 本質上不會更快」。

## 已確認：時間多花在哪裡

下表由六趟 `task.json` 的事件時間與 `wholebody.json` 的 `UNFOLD` 事件重新計算，單位為模擬秒，取各組三趟平均。各段為相鄰事件差，不重複計時；「求解上線→開始進場」包含斜坡、追蹤與穩定判定，**不是純等待或求解成本**。

| 事件區間 | 停車 | MotM | MotM − 停車 |
|---|---:|---:|---:|
| UNFOLD→ALIGN | 7.76 | 5.51 | −2.25 |
| ALIGN→solver_up | 0.81 | 0.25 | −0.56 |
| solver_up→align=approach | 0.74 | 4.53 | **+3.79** |
| align=approach→OPEN | 5.83 | 5.77 | −0.06 |
| OPEN→RELEASE_WAIT（開／保持／關／保持） | 19.60 | 19.53 | −0.07 |
| RELEASE_WAIT→RETREAT | 0.74 | 0.76 | +0.02 |
| RETREAT→RESTOW | 0.53 | 1.89 | **+1.36** |
| RESTOW→HANDBACK_WAIT | 6.23 | 6.98 | +0.76 |
| HANDBACK_WAIT→DONE（交還與回程） | 18.96 | 18.48 | −0.48 |

上表不含去程導航；全程數字沿用 b6 摘要的「開始移動→完成」窗口，不能把上表合計冒稱全程。展開邊界採 `UNFOLD→ALIGN`，與採用展開節點完成宣告的分段數字會略有不同，不能混用。

**分析結論：** 展開及求解上線省下約 2.81 s，主要被進場前多花的 3.79 s 與退開多花的 1.36 s 抵銷。先处理這兩段，比先擴充任務或感知模組更直接對應目前的時間落差。

## 尚未確認：為什麼多花這些時間

- **候選原因 A：軟啟動。** 啟動期手臂補償權重可能讓移動中的 TCP 較慢進入穩定帶；訊息積壓已修正，但不能因此推論軟啟動必定可以移除。
- **候選原因 B：MotM 退開斜坡。** 可能限制退開速度；移除或調整後是否再次衝速、振盪，尚未驗證。
- **候選原因 C：收臂起點與銜接。** 兩組進入收臂時的構型可能不同，需先核既有紀錄，不直接歸因。

**不能說「拿掉兩項就一定省 5.15 s」**：事件區間差不等於可獨立回收的時間，閉迴路動作會互相影響。耗時定位已確認，根因與修法效果仍待確認。

## 下一步：先做時間改善，不改原限制

1. 以本表為瓶頸清單，核對進場前的目標斜坡、軟啟動與穩定計時，先找能移除的重複等待／銜接延遲。
2. 一次只改一個候選機制；先處理進場前，再處理退開。另立改善版本，不改寫 b6、C0、C1a 的凍結結果。
3. 使用相同起終點、行程、完成窗口、速度／加速度／關節限制與夾持／保持判準，與停車策略比較。若修改的是共用工程機制，兩組都應使用修正；若是 MotM 特有銜接，明列策略差異。
4. 同時報全程時間、分段時間、完成／中止、停頓、追蹤、夾持漂移與運動品質。不靠縮短保持時間、放寬判準、放大速度框或刪除失敗趟次取得「較快」。
5. 只有比較資料支持時，才把「MotM 全程縮短」寫成成果；否則記錄有效改善段與仍有的差距，不預設必勝。

WG4-B 仍是第二階段的方法比較待辦；腕部視覺通路與離線觀測成果保留。近期不以擴充這些分支取代本項時間問題。正式改善試跑的設定與安排另行確認，本文件不授權自動啟動模擬。
